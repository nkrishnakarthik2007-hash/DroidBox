# NKK DroidBox compatibility test plan

## Purpose

Measure real Android application compatibility on native Windows. A successful runtime process exit is not proof that an application rendered or worked.

## Test stages

For every APK, record the exact APK version, package ID, ABI, runtime build, Windows build, CPU, RAM, GPU and driver version.

1. Package intake: APK installs/imports; XAPK/APKM/APKS split packages are extracted and resolved correctly.
2. Runtime startup: process starts, package is indexed, Android activity is created.
3. Rendering: first frame appears; portrait/landscape and resize behavior are checked.
4. Input: mouse-to-touch, keyboard, Back, text input and IME are checked.
5. Platform services: files, app-private storage, permissions, networking, audio, media and WebView are checked when used by the app.
6. Persistence: app data survives app restart and DroidBox restart.
7. Stability: 10-minute idle run, 10-minute interaction run, clean shutdown and relaunch.
8. Resource use: record idle and active CPU, private memory, working set, startup time and peak memory.

## Initial app coverage

Use lawful test APKs that the tester is permitted to install. Prefer open-source apps and locally built test APKs.

| Test group | Candidate | Main coverage |
| --- | --- | --- |
| Minimal native UI | DroidBox-owned hello-world APK | Activity lifecycle, text, touch |
| Settings / forms | Locally built form test APK | EditText, keyboard, focus, scrolling |
| File access | Open-source file manager | Storage APIs, SAF, permissions |
| Browser / WebView | Open-source WebView test app | WebView startup, JavaScript, navigation |
| Media | Open-source audio/video test app | Audio, MediaCodec, surface lifecycle |
| Graphics | Open-source GLES sample | EGL, GLES, resize, frame presentation |
| Split package | Test XAPK/APKS generated by our build pipeline | Base APK, split APK and native library selection |
| ARM32 | Locally built armeabi-v7a test APK | ARM32 loader and JNI |
| ARM64 | Locally built arm64-v8a test APK | AArch64 loader and JNI |
| Network | Open-source HTTP test client | DNS, TLS, sockets and connectivity |

## Result vocabulary

- PASS: all required checks for the test case completed.
- PARTIAL: app starts or renders, but one or more required features fail.
- FAIL: app cannot reach its stated test milestone.
- BLOCKED: test cannot be run because a dependency or test environment is unavailable.

Never mark an app as fully compatible based only on process exit code or a splash screen.

## Crash investigation protocol

For every crash, preserve the exact runtime binary and symbols/build identifier. Capture exception code, faulting instruction, registers, call stack, loaded module list and the last runtime log lines. Reproduce with the smallest possible APK before changing runtime code. Confirm a fix by repeating the original reproducer and running regression tests.

## Release gate

A public stable release requires:
- No unresolved blocker crash in the supported test set.
- Native Windows graphics and audio verified on real Windows hardware.
- At least one passing test for ARM32 and ARM64 where supported.
- Package intake, persistence, clean shutdown and relaunch verified.
- Test results published with exact versions and known limitations.
- Third-party licences, notices and source-offer obligations reviewed for every bundled component.

This plan is a test specification, not a claim that the listed tests have already passed.
